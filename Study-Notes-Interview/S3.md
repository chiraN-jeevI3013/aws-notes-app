# S3 (Simple Storage Service)

## Core ideas
- **Object storage:** you store files ("objects") in **buckets**. Each object is found by its **key** (its full name). Objects can be up to 5 TB, and storage is effectively unlimited.
- **No real folders.** `notes/demo/test.txt` is one flat key. The `/` just *looks* like folders, and the console and CLI show "prefixes" as if they were folders.
- **Bucket names are globally unique** across all AWS accounts, which is why we prefix ours: `notes-app-...`.
  - *Why global?* A bucket name becomes part of a **DNS hostname** (`<bucket>.s3.us-east-2.amazonaws.com`), and DNS names must be unique worldwide. It's a constraint of the design, not a feature, and it has no effect on cost.
  - Naming tips: lowercase, 3–63 chars, no underscores. Add something unique (initials, account ID, or a random suffix). Names can't be renamed later, and a deleted name can be grabbed by someone else ("bucket sniping"). Ours: `notes-app-photos-cj`, `notes-app-web-cj`.
- **Encryption at rest:** SSE-S3 (the default, free, AWS-managed keys) vs SSE-KMS (your own KMS keys, with audit trail and key policies, costs per KMS call). **Bucket Key** is only relevant to SSE-KMS: it caches a key per bucket to cut KMS calls and cost. With SSE-S3 it doesn't matter.
- **Object Lock (WORM: write once, read many):** locked objects can't be overwritten or deleted for a retention period, even by root (compliance mode). It needs versioning and can't be turned off once enabled. Use it for compliance (financial records, audit logs) and ransomware-proof backups. **Not** for websites or app data: deploys overwrite files and teardown deletes the bucket.
- **Private by default.** Block Public Access is on, and access is granted via IAM policies, bucket policies, or presigned URLs.

## Reading `aws s3 ls --recursive` output
```
2026-11-14 13:05:14          6 notes/demo/test.txt
   date      time       size(bytes)   key
```
- `6` is the **size in bytes**: `hello` (5 chars) + a newline from `echo` = 6. It's not "6 notes".

## Presigned URLs (how our photos work)
- A presigned URL is a normal S3 URL plus a **signature and expiry** in the query string. It's made by our API using *its* credentials. Whoever holds the URL can do that **one action** (PUT or GET) on **that one key** until it expires.
- Our flow: the browser asks the API for an upload URL → the API returns a presigned PUT (5 min) and a key → the **browser uploads directly to S3** → the browser tells the API "done" → the API saves the key on the note in DynamoDB.
- **Why:** photo bytes never pass through our API (less load, and no Lambda ~6 MB body limit), and the bucket stays private.

## Reading a presigned URL
```
...photo.jpg?X-Amz-Algorithm=AWS4-HMAC-SHA256      ← signing method (SigV4)
  &X-Amz-Credential=<accessKey>/20261114/us-east-2/s3/aws4_request   ← who signed, date, region, service
  &X-Amz-Date=20261114T215420Z&X-Amz-Expires=300   ← valid for 300 s from this time
  &X-Amz-SignedHeaders=content-length;content-type;host   ← these headers must match exactly
  &X-Amz-Signature=88e3...                          ← HMAC over all of the above
```
- The upload URL signs `content-type` and `content-length`, so sending `image/png` to a URL signed for `image/jpeg` → **403 SignatureDoesNotMatch**.
- The view URL signs only `host`, with Expires=3600 (1 hour).
- **PUT to an existing key overwrites it.** S3 has no "already exists" error by default.

## Showing photos in the page: 1 API call + N S3 calls
Clicking a folder with 3 photos = **4 requests**: 1 to our API, 3 straight to S3.
```
1. JS: fetch GET :8080/folders/<id>/notes      → JSON: text + one presigned URL per photo (no image bytes)
2. JS: builds <img src="presigned URL"> per photo (web/index.html, renderNote)
3. Browser: GET :4566/... for each <img>       → image bytes straight from S3, in parallel
```
- **Who starts the image requests?** Not our JS directly. Setting `src` on an `<img>` and putting it on the page makes the **browser** fetch it automatically. That's why DevTools shows those requests with `Sec-Fetch-Dest: image` and `Sec-Fetch-Mode: no-cors`, and the **Initiator** column points to our script's line.
- **Why:** the API sends a few KB of JSON, and the MBs of photo bytes go S3 → browser. Lambda is billed per ms, so it shouldn't stream photos.
- **Caching catch:** every listing signs **new** URLs (new date and signature), so the browser can't reuse cached images, and photos re-download on each click. Prod fix: **CloudFront** (CDN) in front of S3, with signed cookies or stable URLs.
- A **404 NoSuchKey** on one image = a dangling reference (the key is in DynamoDB, the file is gone from S3). The page shows `[missing photo]`.

## Hosting a frontend on AWS: options
| Option | What you get | Notes |
|---|---|---|
| **S3 static website** (ours) | `http://<bucket>.s3-website.<region>.amazonaws.com`, index doc | **HTTP only**, bucket must be public. Fine for learning |
| **S3 (private) + CloudFront** | HTTPS, CDN caching, custom domain; bucket stays private (Origin Access Control) | The production standard |
| **Amplify Hosting** | Git push → build → HTTPS + CDN, branch previews, custom domains | AWS's Vercel/Netlify: S3 + CloudFront + CI packaged. Not in this account's allowed services |
- **Interview line:** "Static frontends go on S3 behind CloudFront: HTTPS, edge caching, private bucket via OAC. Amplify packages that with CI if you want it managed."

## Versioning: when yes, when no
- **What:** S3 keeps every old copy when an object is overwritten or deleted (a delete just adds a "delete marker"). It's an undo button.
- **Yes:** irreplaceable data (user uploads, documents, backups). Pair with lifecycle rules that expire old versions to cap cost.
- **No (our web bucket):** the frontend is rebuildable from Git, so Git *is* the version history. Version IDs are random strings, not "v1.2", so they don't identify releases. Every overwrite stores a full copy, and deleting the bucket needs every version deleted first.
- **Identify which UI is live:** stamp the git commit SHA into the page at deploy (CI/CD, Phase 6).

## Public website bucket: what I saw
- Before upload: `403 AccessDenied`. A missing key without `s3:ListBucket` → 403, not 404 (S3 doesn't reveal what exists).
- "Public" appears in the bucket list's **Access** column and the Permissions overview, not as a banner.
- The policy saving at all proves Block Public Access is off (with it on, S3 rejects a `Principal: "*"` policy).

## One photo upload on AWS, request by request (Chrome DevTools, 2026-11-16)
| # | Row | Goes to | Meaning |
|---|---|---|---|
| 1 | `photo-url` preflight 204 | API Gateway → Lambda | may this page POST JSON? (our middleware says yes) |
| 2 | `photo-url` POST 200 | API | **Step 1:** API checks note, returns presigned PUT URL + key |
| 3 | `<key>` preflight 200 | **S3** | answered by the **bucket's CORS** (S3 replies 200, our API 204) |
| 4 | `<key>` PUT 200 | **S3** | **Step 2:** bytes go straight to S3; Lambda never sees them |
| 5 | `photos` preflight 204 | API | permission for confirm |
| 6 | `photos` POST 200 | API → S3 HeadObject → DynamoDB | **Step 3:** verify file exists, append key to note. **Saved permanently here** |
| 7 | `notes` GET 200 | API → DynamoDB | `loadNotes()` redraws the notes area (not a full page reload), fresh presigned GET URLs |
| 8–9 | `<key>.jpeg` ×2 | **S3** | `<img>` loads (Initiator "Other" = browser). Old photos re-download too: new signature = new URL = cache miss |
- Pattern: 3 steps × (preflight + request) = 6 rows, then 1 list refresh + 1 GET per photo in the folder.
- The photo is saved on confirm (step 3), independent of the **Save** button (which only PUTs title/text). Unsaved *text* is lost on refresh; photos aren't. UX fix: autosave text with a debounce, so everything behaves the same.
